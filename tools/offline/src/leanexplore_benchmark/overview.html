What should the benchmark cover?

This report measures the workload in the supplied log. It identifies sampling risks and query forms worth testing. Search relevance and task success still require judged results.

How much weight do repeated requests receive?

Share of traffic belonging to requests seen once, 2–5 times, or at least 6 times in this window. Same text plus same package filters defines a request. Repetition is not proof of retries, automation or dissatisfaction.

Daily volume

Bars share a zero baseline. The scale uses the largest visible day. Missing dates have no records in this export; this does not establish that the service received no traffic.

What to do with this evidence

  • Build the pilot from distinct requests, stratified by channel and time window. Keep original frequencies as separate workload weights.
  • Include short queries, standalone Lean names, names mixed with text, and longer descriptions. Review the broad "other text" category before inventing semantic labels.
  • Use a channel-balanced score as well as a traffic-weighted score. State the weights: the API-heavy mix should not silently define the whole benchmark.
  • Collect relevant declaration IDs and ranked search results for sampled tasks. Then report retrieval quality, latency and verified task outcomes separately.

The export contains no ranked result IDs, relevance judgments, sessions, latency or verified success. It cannot tell us which engine is better or whether repeating a query means the user was dissatisfied.

Data handling and detailed audit

All displayed counts are rounded to tens. Groups below ten and a complementary cell are suppressed; their labels are withheld. Percentages are approximate and use rounded counts. Suppressed values are unavailable, never zero. Multiple marginal tables are not a formal anonymity guarantee. No raw query, package name, per-query identifier or individual annotation is included.
